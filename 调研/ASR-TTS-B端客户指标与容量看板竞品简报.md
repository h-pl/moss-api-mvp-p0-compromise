# ASR / TTS B 端客户指标与容量看板竞品简报

> 产品范围更新：竞品能力保留作调研证据；Moss 最终采用的 7 类客户核心指标及三个子页面改动，以[《Moss ASR / TTS 核心指标与页面更新说明》](./Moss-ASR-TTS核心指标与页面更新说明.md)为准。

- 日期：2026-09-07
- 范围：MiniMax、豆包语音、讯飞开放平台、Fish Audio、ElevenLabs、腾讯云语音、阿里云智能语音交互；对照当前 Moss API 的用量、服务质量与请求日志候选页
- 方法：PM Skills「Competitor Analysis」框架；官方文档交叉核对；MiniMax 国内开放平台登录态控制台实测

## 一页结论

1. **MiniMax「调用量」可理解为被用量/套餐系统记账的一次模型调用，通常接近 API 请求次数，但不能直接等同于网关收到的所有 HTTP 请求。**公开资料没有说明失败、鉴权失败、限流和自动重试是否计入；它不是 RPM、并发、Token、字符数或音频时长。当前控制台还明确提示“仅统计语言模型”，因此不能拿它代表 ASR/TTS 调用量。
2. **MiniMax 的 API 文档有 RPM、错误码和单请求计量字段，不代表客户后台有相同看板。**本轮实测 MiniMax 国内控制台的「套餐用量」展示调用量、7/30 天趋势、热力图、累计调用量、单日峰值、活跃天数和团队成员用量；未看到语音 ASR/TTS 的 RPM、并发、429、成功率或时延看板。
3. **你的最新候选看板与行业核心指标基本一致，但容量与诊断层明显比多数厂商更深。**请求量、计费用量、成功率、时延、错误、API Key 归因属于合理的客户指标；实时 RPM/并发、利用率趋势和请求级水位证据应降到二级或内部。服务质量首页聚合到 `4xx（不含 429）/429/5xx`，但 429 二级下钻应保留“速率超限/并发超限/服务繁忙”三类，因为三者对应的处理动作和责任不同。
4. **商务担心有道理，但不应把 RPM/并发完全藏掉。**客户自己的合同权益、窗口峰值和真实限流次数应可查，否则限流时会转为工单；分钟级实时水位、上游厂商配额、路由水位和供应商余量应留在内部或高级诊断。
5. **必须区分两套容量。**`客户权益上限` 是 Moss 对客户承诺的资源，应可见；`上游厂商上限` 是供应商给 Moss 的采购与调度资源，不应进入客户看板。上游拥塞不能伪装成“客户超限”。
6. **当前仓库存在口径分叉。**旧主导航服务质量页仍展示 TTS RTF/完整生成、ASR 中间结果/在线 RTF 等偏内部的运行指标；`服务质量5/6` 已收敛为请求成功率、探针可用性、P95/P99、429 和容量摘要。发布前应只保留一套客户口径。

## 1. 先回答 MiniMax：文档里有，用户看板里有吗？

### 1.1 「调用量」到底指什么

MiniMax 当前页面把「调用量」用于 Token Plan/套餐用量统计，官方套餐说明也用“调用次数”描述一定时间窗口内可消费的模型调用。因此，最稳妥的产品定义是：

> **调用量 = 被 MiniMax 用量/套餐系统计入配额的一次模型调用。**它通常与一次 API 模型请求接近，但不是“所有 HTTP 请求尝试数”的同义词。

不能从公开页面进一步推出：

- 失败请求、参数错误、鉴权失败是否计数；
- 被 RPM/并发限制直接拒绝的请求是否计数；
- SDK 自动重试按一次业务调用还是多次 API 请求计数；
- 流式连接中的分片、查询任务接口是否另计一次。

所以 Moss 若展示“调用量”，应直接命名为**计费/配额调用次数**，并在口径说明中明确纳入状态码与重试规则；另用“API 请求数”统计网关实际收到的请求，用“限流拒绝数”统计被容量规则拒绝的请求。三者不应混为一个指标。

页面上某个时点的“调用量”是该统计桶或累计窗口的次数，不是“当前 RPM”。RPM 是一分钟滚动窗口内的请求速率；并发是同一时刻仍在处理的请求/连接数。

来源：[MiniMax Token Plan](https://platform.minimaxi.com/subscribe/coding-plan)、[MiniMax 速率限制](https://platform.minimaxi.com/docs/guides/rate-limits)。

### 1.2 官方 API /套餐层能确认的内容

- 语音 T2A 套餐公开 RPM；不同资源包可为 60/200/500 RPM，商务定制可另议。通用速率限制文档也解释 RPM/TPM，以及主账号和子账号共享限制。
- TTS 单请求响应含 `usage_characters`、`audio_length`、`audio_size`、采样率、码率、声道、`trace_id` 和业务状态。
- 错误码能区分请求频率超限 `1002`、连接数限制 `1041`、请求突增 `2045`、余额不足、内部错误等。
- MiniMax 当前公开 API 目录只查到 TTS，没有查到面向开放平台的 ASR API。若 Moss 使用的是 MiniMax 私有/商务 ASR，需以合同、专属文档和真实控制台为准，不能套用公开 TTS 口径。

来源：[MiniMax 速率限制](https://platform.minimaxi.com/docs/guides/rate-limits)、[MiniMax 语音资源包](https://platform.minimaxi.com/docs/guides/pricing-speech)、[同步 TTS API](https://platform.minimaxi.com/docs/api-reference/speech-t2a-http)、[错误码](https://platform.minimaxi.com/docs/api-reference/errorcode)、[API 能力概览](https://platform.minimaxi.com/docs/api-reference/api-overview)。

### 1.3 客户控制台实测

2026-09-07 在 MiniMax 国内开放平台登录态进入「控制台 → 订阅付费 → 套餐用量」，可见：

- 当前时点调用量、近 7 天调用量、近 30 天调用量；
- 调用趋势图、调用热力图；
- 累计调用量、单日峰值、活跃天数；
- 团队成员用量、套餐与积分余额；
- 页面提示“当前仅统计语言模型，数据可能有延迟”。

本轮未见：

- TTS/ASR 分模型调用趋势；
- 当前 RPM、RPM 峰值或 RPM 利用率；
- 当前/峰值并发或并发利用率；
- 429 次数及频率/连接数原因拆分；
- 成功率、平均/P95/P99 时延、首包时延；
- 请求日志与 `trace_id` 下钻。

因此对 MiniMax 应下结论：**公开“限制值”和单请求字段是有的；语音运行看板没有得到控制台证据支持。**不能把截图中的 RPM 表当作 MiniMax 客户看板已上线的证据。

证据边界：上述结论适用于本轮登录账户所见的国内标准控制台与公开资料；专属企业合同、私有化或定制控制台可能另有页面，若要写成“MiniMax 一定没有”，仍需对应企业账号或厂商书面确认。

### 2.1 ElevenLabs 登录态页面复核（2026-09-07）

因此 ElevenLabs 要拆成三个结论：**API Requests 管“实际请求与运行结果”，Usage 管“计费与语音特有性能/容量”，Request Logs 管“逐请求证据”。**此前把 Credits、TTFB、TTCT、并发都写成 API Requests 页指标是不准确的，本版已更正。

仍需保留两个证据边界：页面和官方帮助中心只给出“成功率”“平均延迟”的名称，没有公开说明成功状态码集合、是否排除客户端取消、延迟起止点以及流式请求以首包还是完成为止。因此可确认**有指标**，但不能直接复制其计算公式到 Moss。Moss 应自行写清分子、分母、成功码、取消/超时处理和时延观测点。

矩阵结论：Moss 在“客户调用证据”上比绝大多数国内厂商更完整；真正偏重的是实时 RPM/并发水位和请求级容量快照。它们应分别进入服务质量二级区块和请求日志，不宜都堆在客户首页。

### 3.2 最新候选 `用量明细5/6 + 服务质量5/6 + 请求日志5/6`

#### A. API 服务质量

| 指标 | 调研判断 | Moss 建议口径 | 页面归属 |
|---|---|---|---|
| API 请求总数 | ElevenLabs 明确作为 API Requests 首要指标；国内厂商也普遍展示调用量 | 网关收到的请求数；与“计费请求数”严格分开 | 服务质量总览；请求日志可核对明细 |
| 请求成功率 | ElevenLabs 明确展示；国内厂商多在 SLA 或错误码层提供 | `成功请求数 / API 请求总数`；明确成功状态码、取消和超时是否进入分母 | 服务质量首屏 |
| `4xx（不含 429）/429/5xx` | 厂商通常先按状态/错误码表达；429 是容量问题，值得从普通 4xx 单列 | 三组互斥，避免 429 同时计入 4xx；超时无 HTTP 响应时并入服务错误或单列“超时” | 服务质量首屏趋势与占比 |
| 429 二级原因 | MiniMax 区分请求频率、连接数和请求突增；ElevenLabs 区分并发超限与系统繁忙；豆包、腾讯、阿里将 QPS 与并发分开 | **保留三级：请求速率超限、并发超限、服务繁忙/容量保护。**不再向客户细分队列、供应商、上游账号或内部路由 | 服务质量点击 429 后下钻；请求日志显示单请求标准错误码 |
| 时延 P50/P95/P99 | ElevenLabs 默认平均值；Moss 的分位数更适合识别长尾 | 首屏 P50/P95，P99 放详情；仅统计成功请求并显示样本数 | 服务质量 |
| TTS TTFB / ASR TTCT | ElevenLabs 放在 Usage 而非 API Requests；只对相应语音模式有意义 | 流式 TTS 展示首音频 P50/P95；实时 ASR 展示最终转写时延 P50/P95；必须注明观测点 | 服务质量的模型/模式区块 |
| RPM/QPS 峰值、上限与利用率 | MiniMax 公布 RPM 上限；豆包、腾讯、阿里展示 QPS 峰值/监控 | 按接口真实限速单位展示客户生效上限、所选窗口峰值和 `峰值/上限` 利用率；QPS 与 RPM 不混写 | **服务质量首屏容量摘要** |
| 并发峰值、上限与利用率 | 豆包、腾讯、阿里公开并发峰值/监控，ElevenLabs 展示并发最大使用量 | 展示客户生效并发上限、所选窗口峰值和 `峰值/上限` 利用率；当前瞬时并发与分钟曲线按需展开 | **服务质量首屏容量摘要** |
| 请求证据 | ElevenLabs 有 Request Logs 与 Trace ID，讯飞/MiniMax 也返回 `sid/trace_id` | `request_id/trace_id`、状态码、模型、时延、错误码、计量值可检索 | 请求日志 |

429 方案选择：**首页不展开原因，保持 `4xx（不含 429）/429/5xx`；点击 429 后只分“速率/并发/服务繁忙”三类。**这是可行动性与商务解释成本之间的平衡：速率和并发需要不同扩容动作，服务繁忙又不能归咎于客户；更底层的供应商与队列原因留在内部。

#### B. 调用量与计量

| 指标 | 调研判断 | Moss 建议口径 | 页面归属 |
|---|---|---|---|
| API 请求数 | ElevenLabs 单独放在 API Requests；MiniMax“调用量”口径不够透明 | 网关收到的请求次数，包括成功和失败；不等于计费次数 | 用量明细辅助指标；服务质量主指标 |
| 计费/配额调用次数 | ElevenLabs 明确说明可能与实际请求数不同，WebSocket 可能计为多个计费请求 | 由 MeterEvent 产生的计量次数；帮助文案写清失败、重试、流式和异步查询规则 | 用量明细 |
| TTS 计费字符/bytes | 豆包、讯飞、腾讯、ElevenLabs 均能确认，Fish 按 UTF-8 bytes | 按客户计费规则统一展示字符或 bytes，不混用；支持按模型/API Key/用户拆分 | 用量明细；费用概览仅显示汇总 |
| ASR 计费音频时长 | 豆包、腾讯、阿里明确，Fish 按音频小时 | 以进入计费的有效音频时长为准；写清进位和最小计费单位 | 用量明细；费用概览仅显示汇总 |
| 积分/费用/资源包 | 七家普遍提供额度、Credits 或资源包信息 | 本期费用、抵扣积分、余额、资源包已用/剩余分开 | 费用概览；用量明细提供计量构成 |
| 模型/API Key/用户/时间 | ElevenLabs 维度最全；豆包/阿里按应用或项目 | 客户维度默认开放；`provider` 和上游账号禁止成为客户筛选项 | 用量明细 |
| 日/小时趋势与导出 | 豆包、腾讯、阿里、ElevenLabs 均支持趋势或报表 | 默认日粒度，短窗口可切小时；标注时区、数据更新时间并支持 CSV | 用量明细 |

结论：Moss 的指标集合本身合理，但应把“服务结果”与“计费消费”拆开。请求总数、成功率、错误和时延属于 API 服务质量；计费次数、字符、音频时长、积分和费用属于调用量/计量。两边可以交叉引用同一个请求，但不能共用一个模糊的“调用量”定义。

### 3.3 旧主导航服务质量页

旧页还展示 TTS RTF、完整生成率、ASR 首个中间结果/最终结果和在线 RTF 等偏内部运行指标。它们并非七家厂商默认客户运行看板的共同做法。

建议：

- 在线 RTF、空结果、完整生成、解码/截断、重连、说话人错分留给内部 SRE/算法；
- 发布前让旧页退出主导航，避免两套口径并存。

## 4. RPM / 并发到底怎么透出，才不让商务被追问

### 4.1 不建议完全隐藏

完全隐藏会产生三个反效果：客户无法做容量规划；429 后只能找商务；合同里写了并发/RPM 时，平台反而缺少交付证据。豆包、腾讯云、阿里云和 ElevenLabs 已证明“容量可见”本身是行业合理做法。

### 4.2 推荐三层可见性（嵌入现有页面）

| 层级 | 面向谁 | 展示内容 | 不展示 |
|---|---|---|---|
| 服务质量默认层 | 全部有权限客户 | 成功率、P50/P95、`4xx（不含 429）/429/5xx`；RPM/QPS 峰值/生效上限/利用率；并发峰值/生效上限/利用率；数据更新时间 | 429 细因、当前瞬时与分钟级水位、上游厂商名与上游余量 |
| 429/容量下钻层 | Owner/Admin/Developer | 429 按“速率超限/并发超限/服务繁忙”三类；当前瞬时 RPM/QPS/并发与分钟级趋势；关联请求日志 | 队列内部阈值、供应商账号总配额、成本、其他租户占用 |
| 内部运营层 | SRE/运营/商务支持 | 七家上游账号额度与水位、队列、路由、重试、熔断、成本、毛利和完整故障原因 | 不直接对客户开放 |

这三层不是三个新页面：前两层都放在「API 监控（现名调用日志）→ 服务质量」及其抽屉中，逐请求证据回到「请求日志」；第三层属于内部运营台。

### 4.3 默认卡片文案建议

不要把“当前 RPM 248/250”放在客户首页大卡。默认改成：

> 容量状态：近 24 小时峰值 78%，未发生客户配额拒绝。当前权益为 250 RPM / 35 路并发。容量数据每 5 分钟更新，仅用于调用规划，不代表供应商或平台整体资源。

只有发生客户侧限流时再突出：

> 近 24 小时有 12 次请求命中客户并发上限。查看请求证据 / 联系管理员调整权益。

若是供应商拥塞，应写：

> 近 24 小时有 4 次服务侧繁忙或上游容量保护，未计入客户超限。平台已记录并纳入服务质量排查。

### 4.4 产品规则

- 上限只显示 Moss 对该企业/模型生效的 `customer_effective_limit`，禁止返回 `provider_account_limit`。
- 客户首页只展示 429 总量；429 下钻归并为 `RATE_LIMIT`、`CONCURRENCY_LIMIT`、`SERVICE_BUSY` 三类。
- 内部仍保留更细的 `limit_reason`，包括队列、上游账号、供应商原始错误和未知原因，用于路由与责任排查，但不形成客户看板维度。
- 客户水位低于其权益但因上游拥塞失败，责任归服务侧，不允许显示“客户容量不足”。
- 默认用窗口峰值与拒绝次数；实时水位和分钟曲线按需展开，不主动制造持续关注。
- 告警阈值由客户管理员设置；平台给建议值但不把 80%/95% 染色直接解释成违约。
- 每个指标显示窗口、粒度、数据延迟、样本数和规则版本；避免商务被追问“为什么刚调了还没变”。
- 扩容入口提供可复制的最小证据摘要，不做“立即购买”式强推，也不承诺自动扩容。

## 5. 建议：不同页面、不同模型支持哪些指标

### 5.1 按页面拆分

客户信息架构保持两组四子页，不新增“容量诊断”客户页面：

| 一级导航 | 子页面 | 页面任务 | 首屏指标/内容 | 二级与下钻 | 明确不放 |
|---|---|---|---|---|---|
| 费用中心 | **费用概览** | 回答“花了多少、还剩多少” | 本期费用、积分抵扣、资源包已用/剩余、账户余额、较上期变化 | 按产品/模型的费用构成、余额或资源包预警 | API 成功率、时延、上游采购价与毛利 |
| 费用中心 | **用量明细** | 回答“哪些调用产生了计量与费用” | 计费/配额调用次数、TTS 计费字符、ASR 计费音频时长、积分/费用；模型/API Key/用户/时间筛选 | 日/小时趋势、计量事件、计费规则说明、CSV 导出；API 请求数作为辅助对照 | 成功率、P95/P99、429 原因、上游厂商维度 |
| API 监控（现名“调用日志”） | **请求日志** | 回答“某次请求发生了什么” | `request_id/trace_id`、时间、模型、模式、状态码、标准错误码、单请求时延、计量值、API Key/用户 | 路径/状态/时延筛选，异步 `task_id` 状态链，导出；可跳转对应质量时间窗 | 聚合 KPI 大卡、供应商账号和其他租户数据 |
| API 监控（现名“调用日志”） | **服务质量** | 回答“API 整体是否稳定、容量是否足够、客户是否需要处理” | API 请求总数、成功率、P50/P95、`4xx（不含 429）/429/5xx`；**RPM/QPS 峰值/生效上限/利用率、并发峰值/生效上限/利用率**；样本数和更新时间 | P99；当前瞬时 RPM/QPS/并发与分钟曲线；429 按速率/并发/服务繁忙三类下钻；按模型/模式展示 TTS TTFB、ASR TTCT | 计费金额、上游厂商/账号和队列细因 |

“调用次数”建议拆成两个并列指标：`API 请求数` 反映 Moss 网关收到多少请求；`计费/配额调用次数` 反映有多少次进入计量。帮助文案明确失败、限流、重试、异步查询是否计数，避免复刻 MiniMax 公开页面的口径歧义。

结构判断：**四个子页面合理，建议仅把一级导航“调用日志”改为“API 监控”。**因为“服务质量”是聚合分析，不属于日志；若暂时不改名，也不影响首发，但不建议再增加第五个“容量”子页面。内部厂商运营台保持独立，不进入客户四子页。

### 5.2 按模型/调用模式启用

| 模型/模式 | 必须支持 | 建议支持 | 不适用或不要默认展示 |
|---|---|---|---|
| TTS 同步、一次性返回 | 请求数、计费字符、成功率、4xx（不含 429）/429/5xx、完整响应时延 P50/P95、生成音频时长、客户 RPM/QPS 峰值与生效上限 | P99、音频/字符比、取消或失败原因、分钟级速率趋势 | 流式首包指标 |
| TTS 流式 | 请求数、计费字符、成功率、首音频时延 P50/P95、流完成率、客户并发峰值/生效上限/利用率、429 | P99、端到端完成时延、客户端取消/断连、当前并发与分钟曲线、RTF 作为高级诊断 | 把首包时延与全文生成时延混成一个“延迟” |
| ASR 短音频同步 | 请求数、计费音频时长、成功率、端到端识别时延 P50/P95、4xx（不含 429）/429/5xx、客户 QPS/RPM 峰值与生效上限 | P99、空结果率、热词/语言配置归因、分钟级速率趋势 | 流连接并发、首个中间结果时延 |
| ASR 实时/流式 | 会话数、计费音频时长、连接成功率、首个中间结果时延、最终结果时延、正常结束率、客户并发峰值/生效上限/利用率、429 | 重连/断连、空转写、当前并发与分钟曲线、在线 RTF、音频时长分桶 | 仅用 RPM 描述长连接容量；异步任务排队 |
| ASR 录音文件/异步 | 任务提交数、提交成功率、任务完成率、计费音频时长、排队/处理/端到端时延、提交/查询 QPS 峰值与生效上限 | `task_id` 状态链、超时/取消、文件时长分桶、分钟级 QPS 趋势 | 用“连接并发”替代任务 QPS；流式首包时延 |
| ASR 说话人分离/识别增强 | 继承对应 ASR 调用模式的请求、用量、错误、时延与容量指标 | 说话人数量/片段作为请求输出字段 | 不增加额外的客户首页指标 |

### 5.3 发布优先级

四个子页面都属于客户首发范围，但按数据依赖分两批：先建立可核对的明细事实，再发布聚合结果。

| 发布批次 | 一级导航 / 子页面 | 首发范围 | 发布门槛 |
|---|---|---|---|
| **P0-A：事实底座** | API 监控 / **请求日志** | request/trace ID、时间、模型/模式、状态码、错误码、单请求时延、计量值、API Key/用户；基础筛选 | 与网关日志抽样核对；状态码和时延观测点稳定；敏感字段脱敏和权限完成 |
| **P0-A：事实底座** | 费用中心 / **用量明细** | 计费调用次数、TTS 字符、ASR 音频时长、积分/费用；模型/API Key/用户/时间筛选；计费口径说明 | 与 MeterEvent、账单和请求日志可对账；失败、重试、流式、异步规则明确 |
| **P0-B：客户聚合** | 费用中心 / **费用概览** | 本期费用、积分抵扣、资源包已用/剩余、余额、较上期变化、产品/模型构成 | 汇总与用量明细一致；明确数据延迟、时区和结算周期 |
| **P0-B：客户聚合** | API 监控 / **服务质量** | API 请求总数、成功率、P50/P95、4xx（不含 429）/429/5xx；**RPM/QPS 峰值/生效上限/利用率、并发峰值/生效上限/利用率**；样本数、更新时间 | 聚合可从请求日志复算；成功率分母、超时/取消规则和错误互斥关系明确；容量上限必须是客户生效权益而非上游配额 |

P0-A 与 P0-B 可以在同一版本发布，但验收顺序必须先明细、后聚合；否则客户无法解释费用或质量大卡为什么变化。

| P1 增强页面 | 增强项 |
|---|---|
| 费用概览 | 费用预测、余额/资源包预警、更细费用构成与账单导出 |
| 用量明细 | 小时粒度、CSV、MeterEvent 下钻、计费规则版本与调用数/计费数差异解释 |
| 请求日志 | 异步 `task_id` 状态链、复制 Trace ID、导出、关联服务质量时间窗、调用时客户容量快照 |
| 服务质量 | P99、TTS TTFB、实时 ASR TTCT；429 按速率/并发/服务繁忙三类下钻；当前瞬时 RPM/QPS/并发和分钟级趋势 |

上游厂商账号、采购配额、水位、价格、路由、队列细因和毛利仅进入内部运营台，不进入四个客户子页面。

## 6. 产品决策

建议采用：**费用中心 + API 监控（现名调用日志）的四个客户子页面 + 内部厂商运营台**。

- 客户页面保持「费用概览、用量明细、请求日志、服务质量」，不增加独立容量页；
- 建议把一级导航“调用日志”改为“API 监控”，使其能同时容纳日志与聚合质量；
- 先验收请求日志和用量明细，再验收费用概览和服务质量的聚合；
- 服务质量首页展示 `4xx（不含 429）/429/5xx`，429 二级只分速率、并发、服务繁忙三类；
- 当前 RPM/并发、分钟级曲线和请求级水位放服务质量二级区块；默认只展示窗口峰值、生效权益和 429 总数；
- `provider`、上游账号额度和供应商容量绝不作为客户维度；
- 旧服务质量页中的偏内部算法指标退出默认运行看板；
- 对外话术统一为“客户调用权益与运行证据”，不要称“厂商容量看板”。

这样既能与豆包、腾讯云、阿里云和 ElevenLabs 的客户可见性对齐，也能避免把 Moss 的供应链和实时运营压力变成商务每日解释的对象。

## 7. 基于原目录树的导航命名建议

总体结构不需要重排，只建议改一个一级导航名称：`调用日志` → `API 监控`。其余名称与当前页面任务一致，保留能减少用户学习和迁移成本。

建议目录树：

**管理**

- **凭证与授权**
  - API 凭证
  - 音色授权
- **费用中心**
  - 费用概览
  - 用量明细
- **API 监控**（原“调用日志”）
  - 请求日志
  - 服务质量

**组织**

- **企业管理**
  - 企业与用户
  - 企业认证
  - 操作审计

命名判断：

| 原名称 | 建议名称 | 是否调整 | 原因 |
|---|---|---:|---|
| 凭证与授权 | 凭证与授权 | 否 | 能同时覆盖 API 凭证和音色授权 |
| API 凭证 | API 凭证 | 否 | 比“API Key”覆盖面更宽，适合包含密钥、状态、权限和生命周期的页面 |
| 费用中心 | 费用中心 | 否 | 与费用概览、用量明细的父子关系清楚 |
| 调用日志 | **API 监控** | **是** | “调用日志”只能解释请求明细，无法自然包含聚合型“服务质量”；“API 监控”可同时覆盖两者 |
| 企业管理 | 企业管理 | 否 | 企业主体、用户、认证和审计均属于企业治理 |
| 企业与用户 | 企业与用户 | 否 | 当前页面若同时包含企业资源和用户管理，名称比单纯“成员管理”更准确 |

若产品希望全部使用中文，也可用“调用监控”，但不建议使用“运行中心”“可观测中心”等偏内部运维的名称；对 B 端客户而言，“API 监控”最直接。
