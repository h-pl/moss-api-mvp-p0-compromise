# V3 迭代后 PM 核对与本轮修正

> 2026-09-02 范围校准：本评审中的“应用/调用账号/服务账号”历史表述以当前 PRD 为准，客户侧统一收敛为 Project 下的 API Key；项目是唯一资源边界。

评审日期：2026-08-31  
方法：pm-skills `intended-vs-implemented`、`prioritize-features`  
实现约束：`b2b-vibe-prototype`、`api-and-interface-design`、Frontend Design Premium

## 1. 产品目标

V3 不是开放式云市场，而是已签约企业客户的交付补充控制台。核心结果是：客户能管理机器调用身份，按项目和凭证核对用量，通过 request_id 查看服务证据，并理解合同服务质量口径；成员只承担授权和审计责任。

## 2. 意图与实现核对

| 优先级 | 文档意图 | 核对前实现证据 | 风险 | 本轮处理 |
|---:|---|---|---|---|
| P0 | Role + Project Scope 同时决定数据范围 | `V3App.tsx` 的项目切换只改变顶栏文字；日志、用量和凭证列表未消费该状态 | Developer 可看到范围外的 mock 数据，削弱 RBAC 逻辑表达 | 增加统一 `ProjectContext`；角色切换重新解析范围；凭证、用量、Playground、日志和质量页消费同一上下文 |
| P0 | Key 生命周期必须包含创建、轮换、停用和审计后果 | `KeyDetail` 的轮换与停用只触发 Toast | 核心凭证治理链无法完成演示 | 增加轮换迁移窗口、一次性新密钥、停用影响确认和可见状态变化 |
| P1 | 客户通知应能回到业务对象 | 顶栏通知按钮只显示一条聚合 Toast | 配额、结算、成员事项无法进入处理页 | 增加通知抽屉、三类对象跳转、已读状态与角标联动 |
| P1 | Playground 应表达成功和关键失败责任 | 仅有 200 成功态 | 无法解释 429 为什么不计入不可用、504 为什么进入服务方异常 | 增加 200/429/504 演示结果、统一错误码、request_id、计量与责任提示 |
| P1 | 同一用量在各维度必须可加总 | 旧版服务账号列表按 ID 字符串推断请求数，两个生产对象重复显示相同请求数与费用 | 客户对账时数据自相矛盾 | 收敛为 Project/API Key 明细 fixture；总请求与费用可加总；补齐“模型”维度 |
| P1 | 日、周、月及项目筛选必须使用各自统计口径 | 切换日/周后仍显示“月度口径”和 44,640 分钟公式；切换项目只改变范围文字 | 服务质量证据口径错误 | 为日/周/月和项目范围分别定义总分钟、不可用分钟、成功率、P95、异常数与排除项 |
| P2 | 首页动作必须符合当前角色 | Finance 首页仍出现管理服务账号和定位请求入口，点击后才显示 403 | 增加认知负担，权限表现不一致 | 首页主动作、关注事项和快捷入口按角色隐藏；路由级 403 继续保留为第二道保护 |
| P2 | 创建项目和 API Key 是凭证治理的必要子链 | 两个主按钮仅显示“表单已打开”的 Toast | 主流程有死按钮 | 增加表单、校验、后续动作说明，并把新对象即时回写列表 |
| P1 | 数据范围必须覆盖结算卡与汇总指标 | 切换项目后表格已过滤，但结算卡仍显示企业总费用 | 同一页面出现两套相互冲突的费用口径 | API 费、并发费、预计合计和模型成功率统一消费项目范围 |

## 3. 优先级说明

采用 Impact × Confidence × Ease 的轻量 ICE 判断。项目范围和 Key 生命周期直接跨越数据与安全边界，优先于视觉增强；通知、失败态和计量一致性决定演示能否在不口头补充的情况下讲清；营销型页面和更多模型展厅内容不影响本轮企业交付目标，继续降级。

## 4. 本轮仍不实现

- 真实 IAM/RBAC、数据库和多租户隔离
- 真实密钥生成、托管、轮换和吊销
- 真实 API 请求、网关日志和 MeterEvent
- 短信/邮件/企业微信通知发送
- 真实账单、发票、支付认款和合同确认

这些能力需要后端才能形成可信边界。原型只展示状态、交互后果和对象关系，不把 mock 结果描述为真实生产事实。

## 5. 回归重点

1. Owner → Developer：数据范围自动收敛到“内部评测”，管理与费用菜单按角色隐藏。
2. 项目与凭证 → API Keys → 管理：可完成轮换和停用流程。
3. Playground：分别运行 200、429、504，并进入对应 request_id 日志。
4. 费用中心 → 用量明细：Project、API Key、模型三种维度的数值一致且受项目范围约束。
5. 调用日志 → 服务质量：日、周、月公式和标签同步变化，且仅提供查询与下钻。

## 6. Beta.3 深化（2026-09-01）

本轮再次使用 `intended-vs-implemented` 核对“企业账号治理、调用日志、服务质量、用量归因”四条核心链路。结论是 Beta.2 的产品名词已经完整，但详情层仍偏静态，客户需要依赖讲解才能理解对象关系。

| 核心问题 | 修改意见 | Beta.3 实现 |
|---|---|---|
| 企业 Owner 无法从成员列表判断账号安全和权限边界 | 成员管理应以登录账号治理为主，不展示个人调用量 | 增加搜索与角色/状态筛选、席位/MFA 概览、成员详情、会话安全、角色与 Project Scope、资源责任和审计记录 |
| 项目只有列表，没有凭证上下文 | Project 应成为 Key、配额、用量和请求证据的父对象 | 增加项目详情、用量趋势、安全边界、最近 request_id 和 API Key 入口 |
| 请求日志只有表格和单条静态侧栏 | 先展示调用态势，再以 request_id 进入证据链 | 增加项目/账号/状态/时间筛选、请求状态趋势、责任分布、分页语义与完整请求证据侧栏 |
| 服务质量仍像静态合同说明 | 合同口径、趋势、时延、事件和原始请求必须在同一查询链 | 增加可用性目标线、时延分位图、责任口径、服务事件列表与事件详情下钻 |
| 用量只有总量和简单折线 | 客户需要从企业总量下钻到 Project、Key、MeterEvent 与费用 | 增加计费用量趋势、Key 占比、结算口径条、项目用量详情、计量规则和 request_id 证据 |

仍不把成员作为调用计费维度：成员是登录和管理身份，生产用量由 `Project → API Key → request_id → MeterEvent` 归因。
