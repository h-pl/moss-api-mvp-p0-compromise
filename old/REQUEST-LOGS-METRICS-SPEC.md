# 请求日志与用量指标口径（v3）

## 1. 目标

请求日志的作用是让企业客户在合同交付范围内，沿着一条可追溯链路核对调用、计量和服务质量：

`Project → API Key → request_id → MeterEvent / 服务指标`

页面展示的是交付证据和运营自助查询，不是内部运营后台，也不将验收动作变成客户侧的“确认”操作。

## 2. 统计主体与维度

### 主维度：API Key

- API Key 是实际发起调用、承载 Scope、配额、IP 限制和生命周期的稳定技术主体。
- 用量、费用、错误率和延迟都应能按 `Project / API Key / 模型 / 时间` 聚合。
- Key 的归属链路为 `Project → Key`；创建成员仅作为审计记录，不作为调用归因。

### 辅助维度：成员

成员统计不是伪需求，但不能通过“谁创建了 Key”推断“谁发起了调用”。只有后端在请求中明确记录并可信传递 `actor_id / caller_subject`（例如员工登录态、服务账号或网关注入的调用主体），才可以提供成员用量视图。

在当前 B 端交付场景中，成员维度默认用于：

- 成员权限、项目范围和凭证管理审计；
- 查看某成员接触过哪些 Key、何时创建/轮换/停用；
- 在后端具备 `actor_id` 后，作为用量的可选辅助筛选，而不是合同计量主口径。

## 3. 请求日志主路径

筛选顺序固定为：

1. 时间范围：近 1 小时、近 24 小时、近 7 天；
2. 项目：全部项目或单一 Project；
3. API Key：在所选 Project 范围内联动；
4. API Key：在所选 Project 范围内联动；
5. 状态 / 责任：成功、客户侧 4xx/429、服务方 5xx/超时。

项目变化时清空 API Key，避免保留的下级条件造成“筛选条件与结果范围不一致”。全文搜索支持 `request_id / Project / API Key / 模型`，点击 request_id 查看证据链。

## 4. 指标分层

### 合同与服务质量

- 服务可用性：仅统计服务方责任的有效请求；客户侧鉴权失败、配额触发、非法参数不计入服务不可用。
- 成功率：`2xx / 有效请求`，同时拆分客户侧 4xx/429 与服务方 5xx/超时。
- 延迟：端到端 P50/P95/P99；按 ASR/TTS 的可交付事件分别统计首包、最终结果和完整生成等指标。
- 事件闭环：每条异常可由 `request_id` 下钻到鉴权、配额、推理、计量和责任判断。

### 用量与对账

- 计量单位以产品规则为准（TTS 字符/音频时长、ASR 音频时长等），由 MeterEvent 产生。
- 聚合维度为 `Project / API Key / 模型 / 时间`；对账需保留规则版本、事件时间和原始 request_id。
- 页面可展示成员辅助视图，但不得替代 API Key 或 MeterEvent 口径。

## 5. 当前原型与后端缺口

- 原型已提供 Project、API Key、状态/责任、时间和全文搜索，并模拟联动清空与证据下钻。
- 原型指标使用示例数据；“请求数”卡片明确标注为当前筛选样本，不冒充生产总量。
- 成员级用量需要后端补充可信的 `actor_id / caller_subject`、脱敏策略和权限校验；在此之前不在客户主导航中承诺成员计量。
- 生产实现还需确定时间窗口、时区、P95 计算方式、迟到事件修正、导出权限和数据保留周期。

## 6. 权限建议

- Owner / Admin：可查看全企业项目范围的日志、用量和服务质量；是否可导出由企业策略控制。
- Developer：仅查看被授予 Project Scope 的日志和指标；凭证管理权限不自动等于全量数据权限。
- Finance：查看用量、费用和对账，不默认获得 Key 明文或凭证管理权限。
- Viewer：只读查看其 Project Scope 内的日志与服务质量。
