# Moss API V3 覆盖率与企业适用性评审

评审日期：2026-08-31  
评审方法：pm-skills `intended-vs-implemented`、`job-stories`、`prioritize-features`

> 实现更新（2026-09-02）：V3 已恢复 V2 全部客户侧一级导航和主要子链，只移除内部运营台；项目是唯一业务资源边界，API Key 直接归属于项目，并已补充成员 RBAC、用量归因、请求证据和合同服务质量查询。本文表格已按本轮实现重新标记；真实 IAM、网关、计量和结算仍属于后端缺口。

## 1. 结论

V3 的最新方向是恢复 V2 的完整客户控制台，并删除内部运营控制面。V2 的发现、体验、交易、开发接入、企业治理和专属交付是客户产品基线；V3 的增量是企业接入治理、用量归因和合同服务信息查询。

当前 V3 对本轮明确的客户原型范围已经形成完整表达：V2 客户侧导航、企业成员与数据权限、机器凭证治理、调用归因、费用用量、请求日志和服务质量可以互相跳转。完整 P0 中的内部运营能力被明确移出 V3，不能计入本客户原型的缺口。

V3 仍不能宣称具备生产能力。页面中的鉴权、密钥、通知、网关遥测、计量、账单和合同指标都是 mock；这些对象只有接入后端并形成不可变证据后，才能用于真实客户交付。

## 4. V2 与 V3 导航结论

### V2

V2 客户端承担模型发现、体验、方案转化、开发接入、费用交易、企业治理和专属交付；另有独立的 Moss Ops 内部运营模式。V3 应复用前者，不迁移后者。

### V3

V3 恢复 V2 客户端的发现、开发、管理和组织四组导航，只删除内部运营入口。服务质量作为 V3 增量归入“调用日志”，不设置“月度报告”或“月度验收”导航。

当前实现遵循两个企业信息架构原则：

1. “团队成员”和“账号与安全”不属于应用凭证。成员属于 Workspace/组织治理；个人登录安全应进入顶栏账号菜单。
2. “调用日志”通过页面内 Tabs 容纳请求日志和服务质量；月度只是服务质量的时间筛选维度。

当前已经采用 V2 客户导航：平台首页；发现（模型与服务、体验中心、解决方案）；开发（Playground、API Docs）；管理（项目与凭证、费用中心、调用日志）；组织（企业管理、专属服务）。子对象继续放在页面内 Tabs 和详情页。

单项目企业应弱化或隐藏顶栏项目切换器；多项目企业才常驻显示。该行为与需求中的“默认项目开箱即用、单项目弱化切换”一致。

## 5. 团队成员是否需要展示个人用量

### 产品结论

生产 API 场景默认不展示“成员个人用量”，也不应把它作为账单归因维度。

原因：企业生产调用通常来自后端服务、定时任务或流水线，真实调用主体是 API Key，不是登录控制台的自然人。若把某个 Key 的全部用量算到创建它的成员名下，会产生错误归因；若鼓励每个人使用个人 Key，又违背机器身份与人员身份分离的企业安全习惯。

正确归因链应为：

`Workspace → Project → API Key → Model/Endpoint → request_id → MeterEvent/Charge`

成员承担的是管理责任和操作审计：

`Member → Role → Project Scope → 创建/轮换/吊销凭证等 AuditEvent`

### 团队成员详情应展示

- 角色、席位、项目/费用/日志数据范围
- 邀请状态、最近登录、MFA、安全状态
- 最近权限变更与高风险操作审计
- 负责或管理的项目、API Key
- 可选的“关联资源用量”入口：跳转到已按项目/Key 过滤的用量页

该入口应写“查看其负责资源的用量”，不能写“该成员消耗了多少”。

### 何时可以有成员维度用量

仅在 Playground、个人开发令牌或明确携带最终用户标识且完成隐私/合规评审时，才可以提供成员级“开发调试用量”。V3 虽保留 Playground，但生产账单和合同指标查询仍以项目和 Key 归因，不能把调试数据等同于成员账单。

## 6. 企业关键 Job Stories

### JS-01 最小权限接入

当管理员要让一个新系统接入生产语音服务时，希望先确定项目和机器身份，再授予最小 Scope，以便调用不依赖员工个人账号。

验收：可创建/选择项目；在项目下创建 Key；设置 Scope、IP、有效期；secret 只展示一次；可轮换和吊销；全流程记录操作者与时间。

### JS-02 成员入离职与权限变化

当员工加入、转岗或离职时，管理员希望调整其 Workspace 角色和项目范围，以便不会影响机器调用，也不会保留越权访问。

验收：邀请可撤回和过期；角色权限可预览；成员可停用；机器凭证不随成员停用而错误失效；高风险变更有二次确认和审计。

### JS-03 调用故障自助诊断

当生产请求失败时，开发者希望用 request_id 判断是鉴权、配额、路由、推理还是计量问题，以便决定修改配置、等待重置或提交支持请求。

验收：按项目/Key/模型/状态筛选；看到完整证据链；错误可跳转文档；责任口径与服务质量一致。

### JS-04 用量和费用核对

当财务或项目负责人准备月度结算时，希望从费用汇总下钻到项目、凭证、日期和请求，以便解释差异并在时限内提出异议。

验收：可按项目、Key、模型和账期筛选；历史规则不回写；Adjustment 单列；汇总可回到 MeterEvent/request_id；Finance 角色只读可见。

### JS-05 合同服务质量核查

当客户核查某个统计周期的服务表现时，希望区分成功率、可用性、观察指标和排除情形，以便理解合同指标和明细数据。

验收：显示合同目标、公式、不可用窗口、排除项、重大事件响应、统计口径和更新时间；可下钻请求；页面不提供验收、确认或异议动作。

## 8. 明确不应补回 V3 的内容

- 内部模型发布、价格审批、支付认款、全租户运营和成本毛利
- 内部 Pod 容量池、资源调度和交付处置台
- Moss Ops 角色切换、全局搜索和内部通知
- 无可靠身份依据的“团队成员个人 API 用量”

模型发现、体验、解决方案、Playground、只读订单权益和客户专属服务继续保留。在线下单、支付、认款、充值和自动开通不进入 V3；采购与履约由商务侧负责。

## 9. 最终判断

V3 已恢复 V2 客户控制台框架并删除在线交易与内部运营台，也已围绕项目、成员权限、用量归因、项目详情和合同质量查询补齐原型闭环。当前版本用于表达签约后的 B 端合同交付价值；真实上线仍需完成第 7 节的后端能力。
